## Var vi är

Nätverksserien tog oss hela vägen till svaret: metoden, statuskoden, headers och kroppen. Du kan
läsa ett HTTP-anrop.

Den här delen handlar om vad man **bygger** med dem. Ett API är inte en teknik utan en
överenskommelse, och HTTP råkar bara vara det vanligaste sättet att uttrycka den. Vi håller oss till
vad ett API är och vilka roller som finns — hur det bör utformas tar nästa del.

## Vad ett API är

Ett **API** är ett kontrakt mellan två system: det här får du fråga om, och det här får du tillbaka.

Kontraktet säger ingenting om hur svaret räknas fram. Den som svarar får byta databas, språk och
algoritm hur den vill, så länge frågorna och svaren ser likadana ut.

Lisas kassa behöver visa fraktpris. Priset beror på vikt, postnummer och vald tjänst, och den
informationen finns hos fraktbolaget. Hon får aldrig tillgång till deras databas — men hon får ställa
en fråga:

```http
GET /v2/priser?vikt=1200&postnr=11122
```

Och får tillbaka:

```json
{
  "pris": 79,
  "valuta": "SEK",
  "leverans": "2026-08-06"
}
```

Lisa fick svaret utan att veta hur det räknades ut. Fraktbolaget svarade utan att släppa in henne
någonstans. Den friheten är inte en bieffekt — den är poängen.

## API vs webbsida

Samma system kan svara på två helt olika sätt beroende på vem som frågar.

**En webbsida** är HTML: ett svar avsett för en människa, med layout, text och knappar. Webbläsaren
ritar upp det.

**Ett API** svarar med data: oftast JSON, avsett för ett annat program. Ingen layout, ingen
formatering — bara värden.

Ofta finns båda för samma information. GitHub har en sida på `github.com/withastro/astro` och samma
uppgifter som JSON på `api.github.com/repos/withastro/astro`. Innehållet är detsamma; formen är vald
efter mottagaren.

Det är därför "API" inte betyder "något separat system". Det betyder ett gränssnitt avsett för
program i stället för för ögon.

## Klient och server

**Klienten** är den som ställer frågan. **Servern** är den som svarar.

I Lisas fall är kassan klient och fraktbolagets system server. När kundens webbläsare hämtar
produktlistan är webbläsaren klient och Lisas system server.

Rollerna definieras alltså av anropet, inte av maskinen.

## Klient vs server

De förväxlas hela tiden, och förväxlingen sitter i att orden också används om maskiner.

**Klient** är rollen som frågar i ett enskilt anrop.

**Server** är rollen som svarar i samma anrop.

Lisas webbshop är klient när den frågar fraktbolaget om priser, och server när kundens webbläsare
frågar den om produkter. Samma system, båda rollerna, olika anrop.

Det förklarar också varför "backend" och "server" inte är synonymer. Ett backend-API som anropar tre
andra API:er är klient tre gånger om.

## Vad en endpoint är

En **endpoint** är en adress i API:et som svarar på en viss sorts fråga.

`GET /v2/priser` är en endpoint. `GET /produkter/8842` är en annan. Adressen och metoden tillsammans
avgör vilken det är — samma sökväg med olika metod är två olika endpoints.

Ordet används löst i vardagen och betyder ibland bara "sökvägen". I den här serien håller vi isär
dem: sökvägen är en del av adressen, endpointen är hela ingången.

## Vad en resurs är

En **resurs** är det API:et handlar om: en produkt, en order, en kund.

Resursen är begreppet, inte lagringen. Att en produkt finns som resurs säger ingenting om huruvida
den ligger i en tabell, i tre tabeller eller hämtas från ett annat system.

Ett API som är byggt kring resurser går att gissa sig till. Det är hela grunden för nästa del.

## Vad JSON är

**JSON** är ett textformat för strukturerad data, och det vanligaste svarsformatet i API:er.

```json
{
  "id": 8842,
  "namn": "Skruvmejsel PH2",
  "pris": 149,
  "iLager": true
}
```

Formatet har fyra sorters värden du kommer att se: text inom citattecken, tal utan, `true`/`false`
och `null`. Därtill objekt inom klamrar och listor inom hakparenteser.

JSON är läsbar text, precis som HTTP självt. Det betyder att du alltid kan titta på vad som skickas
i stället för att gissa.

## Resurs vs databasrad

Den här skillnaden är den som avgör om ett API åldras väl.

**Databasraden** är hur något lagras: alla kolumner, inklusive interna som `inkopspris`,
`leverantor_id` och `senast_andrad_av`.

**Resursen i svaret** är en **representation** — en version vald för det här sammanhanget, med bara
de fält mottagaren ska se.

De två råkar likna varandra i början, vilket är precis det som gör förväxlingen farlig.

<Callout type="fallgrop" title="Att skicka hela raden">
Det bekvämaste sättet att bygga en endpoint är att hämta raden och returnera den rakt av:

```js
const produkt = await db.query(
  "SELECT * FROM produkter WHERE id = $1", [id]);
res.json(produkt);   // ← allt som råkar finnas i raden
```

Det fungerar — tills någon lägger till en kolumn. Då börjar API:et skicka ut den också, utan att
någon bestämt det. På användartabeller är det så här `losenord_hash` och `ar_admin` läcker ut, och
`SELECT *` gör att ingen märker det i kodgranskningen.

Välj fälten uttryckligen. Det är fem sekunders extra arbete och den enda versionen som håller över
tid.
</Callout>

## Varför frontend inte pratar med databasen

Det är en rimlig fråga, särskilt när API:et till en början bara ser ut att skicka vidare det
databasen redan har.

## Validering i klienten är ingen validering

Den punkten är värd en egen sektion, för den gör frågan ovan avgjord snarare än en avvägning.

Kontroller i webbläsaren hjälper användaren att fylla i rätt. De hindrar ingen från att skicka ett
anrop direkt till API:et, utanför sidan, med vilket innehåll som helst.

`curl` räcker för att gå förbi varje regel som bara finns i frontend. Regeln måste därför finnas där
data faktiskt tas emot — i API:et.

Klientvalidering är alltså inte onödig. Den är bara inte skydd.

## Vad ett kontrakt förpliktar till

Så länge någon använder ditt API är formen på svaret ett löfte.

Att byta namn på ett fält, ta bort det, eller ändra dess typ är en **brytande ändring**: klienter som
fungerade i går slutar fungera i dag utan att de ändrat något.

Att *lägga till* ett fält är däremot normalt ofarligt, eftersom klienter som inte känner till det
bara ignorerar det.

Det är den asymmetrin som gör API-design värd omsorg: det är lätt att lägga till och dyrt att ändra.

## Internt vs publikt API

Hur mycket omsorg som är rimlig beror på vem som är på andra sidan.

**Ett internt API** är det Kubernetes-serien beskrev: `http://api:5000`, nåbart bara inifrån klustret,
med ett känt antal klienter du själv äger. Ändras kontraktet ändrar du klienterna samtidigt.

**Ett publikt API** — som fraktbolagets — har klienter du varken känner till eller kan kontakta. Där
blir kontraktet ett löfte du inte kan bryta ensidigt, och det är därför versionering, dokumentation
och stabila fältnamn plötsligt är avgörande.

Att bygga ett internt API som om det vore publikt är slöseri. Att bygga ett publikt som om det vore
internt är ett löfte du kommer att bryta.

## Vad det här betyder i ditt arbete

Du kommer att anropa API:er varje dag och bygga dem inom kort. Det du gör oftast är att läsa ett
svar och avgöra om fältet du behöver finns, heter något annat, eller aldrig var tänkt att skickas.

Två vanor från det här avsnittet betalar sig direkt: välj fälten uttryckligen i stället för att
returnera raden, och lägg varje regel som betyder något i API:et, inte i formuläret.

Autentiseringsflöden, rate limiting och API-gateways kan vänta. De blir aktuella när API:et fått
klienter du inte äger — och då är det fortfarande samma kontrakt du skyddar.

## Vanliga nybörjarförväxlingar

Ett API är inte en teknik. Det är ett kontrakt, och HTTP är bara det vanligaste sättet att uttrycka
det.

Ett API är inte en webbsida. Sidan är för ögon, API:et för program — ofta med samma information
bakom.

Klient och server är inte maskiner. De är roller i ett enskilt anrop, och samma system kan ha båda.

Resursen i svaret är inte databasraden. Den är en vald representation.

Validering i webbläsaren är inte skydd. Den går förbi med ett anrop utanför sidan.

Att lägga till ett fält bryter normalt ingenting. Att byta namn på ett gör det.

## Prova själv

Alla kommandon nedan bara läser, mot ett publikt API som inte kräver inloggning.

Hämta ett svar och titta på det:

```bash
curl -s https://api.github.com/users/BeeBarry
```

Du får JSON: klamrar, fältnamn inom citattecken, tal utan. Jämför sedan vad samma server svarar med
för en människa respektive för ett program:

```bash
curl -s -o /dev/null -w "%{content_type}\n" \
  https://github.com/BeeBarry
```

```bash
curl -s -o /dev/null -w "%{content_type}\n" \
  https://api.github.com/users/BeeBarry
```

Första svaret är `text/html`, det andra `application/json`. **Samma information, två
representationer** — vilket är exakt vad avsnittet om API vs webbsida beskrev.

Titta slutligen på hur många fält svaret faktiskt innehåller, och fråga dig vilka av dem GitHub valt
att ta med och vilka som ligger kvar i deras databas.

Två saker som kan förvirra: utan inloggning tillåter GitHub omkring sextio anrop i timmen, och
därefter får du `403` med ett meddelande om rate limit — det ser ut som ett behörighetsfel men är en
hastighetsgräns. Och `curl` utan `-s` skriver ut en förloppsindikator som blandas med svaret.

## Snabb sammanfattning

- Ett API är ett kontrakt: det här får du fråga om, det här får du tillbaka.
- Kontraktet säger ingenting om hur svaret räknas fram. Den friheten är poängen.
- En webbsida svarar med HTML för ögon; ett API med data för program.
- Klienten frågar, servern svarar — roller i ett anrop, inte egenskaper hos en maskin.
- En endpoint är adress plus metod. Samma sökväg med olika metod är två endpoints.
- En resurs är det API:et handlar om, inte hur det lagras.
- JSON är läsbar text. Du kan alltid titta på vad som skickas.
- Svaret är en vald representation av resursen — inte databasraden.
- Frontend pratar med API:et, aldrig med databasen. Uppgifter i en webbläsare är publika.
- Validering i klienten är hjälp, inte skydd.
- Att lägga till ett fält är normalt ofarligt. Att byta namn på ett är en brytande ändring.
- Internt API = klienter du äger. Publikt API = ett löfte du inte kan bryta ensidigt.

## Nästa del

Nu vet du vad ett API är och vilka roller som finns. I nästa del går vi från *vad* till *hur*: hur
sökvägar namnges och struktureras så att den femtionde endpointen är lika förutsägbar som den första.
