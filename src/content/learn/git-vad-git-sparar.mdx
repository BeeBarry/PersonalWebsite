## Var vi är

Git har funnits i bakgrunden genom hela Learn Hub. Terraform-filerna skulle ligga i ett repo,
merge requesten var där infrastrukturändringen granskades, och `.dockerignore` fungerade
"precis som `.gitignore`".

Den här delen tar Git självt, och börjar inte med kommandon. Nästan all Git-förvirring kommer
från en enda felaktig bild av vad som sparas. Rättas den bilden blir kommandona lätta.

## Vad Git är

Git är ett versionshanteringssystem. Det sparar hur ett projekt såg ut vid olika tidpunkter, så
att du kan gå tillbaka till vilken som helst av dem.

Git körs lokalt på din dator. Hela historiken ligger i en dold mapp som heter `.git` i
projektmappen, och du behöver varken internet eller ett konto för att använda den.

Git är inte en säkerhetskopia. En säkerhetskopia sparar det senaste; Git sparar varje läge du
själv har markerat som ett läge värt att spara.

## Git vs GitHub

De två blandas ihop nästan alltid, och de är olika saker.

**Git** är programmet på din dator. Det skapar historiken.

**GitHub** är en webbtjänst som lagrar en kopia av ett Git-projekt så att flera personer kommer
åt det. GitLab, Bitbucket och Azure DevOps gör samma sak.

Du kan använda Git i åratal utan GitHub. Du kan däremot inte använda GitHub utan Git — tjänsten
lagrar Git-projekt.

## Repository

Ett **repository**, i dagligt tal ett repo, är ett projekt som Git håller reda på.

Ett repo skapas med `git init` i en mapp. Det som händer är att Git lägger till mappen `.git`.
Där bor historiken, och resten av mappen är dina vanliga filer.

Kopierar du `.git`-mappen har du kopierat hela historiken. Raderar du den har projektet fortfarande
alla sina filer, men ingen historik alls.

## Vad en commit är

En **commit** är ett sparat läge i projektet.

Du bestämmer själv när ett läge ska sparas, och du ger det en beskrivning i samma stund. Det är
det som skiljer en commit från en autosparad fil: commiten är ett medvetet påstående om att
*här är en punkt värd att kunna återvända till*.

## Ögonblicksbild, inte ändringar

Det här är den felaktiga bilden som orsakar mest problem.

Diffen du ser i `git diff` är alltså inte det som lagrats. Den räknas ut i stunden, genom att
jämföra två ögonblicksbilder.

Att bilderna är billiga beror på att Git inte sparar oförändrade filer på nytt utan återanvänder
dem. Det är en optimering under huven, och den behöver du inte kunna. Bilden du ska tänka i är
ögonblicksbilder.

## Vad som står i en commit

Fyra saker, varje gång:

```txt
ögonblicksbilden   hela filträdet som det såg ut
föräldern          vilken commit som kom före
metadata           vem, när, och meddelandet du skrev
hashen             commitens namn, t.ex. a3f9c2e
```

Föräldern är det som gör historiken till en kedja. Den allra första commiten i ett repo saknar
förälder, och är den enda som gör det.

## Hashen

Hashen är commitens namn. Den ser ut som `a3f9c2e1b4d8…` och är inte ett löpnummer.

Hashen räknas ut ur commitens innehåll: filerna, meddelandet, tidpunkten och föräldern. Ändras
en enda bokstav i något av det blir hashen en annan.

Det ger två garantier som är värda att förstå:

- Två utvecklare med samma hash har garanterat exakt samma kod.
- Historik går inte att ändra i smyg. Ändras något bakåt i kedjan får alla efterföljande commits
  nya hashar, eftersom var och en innehåller sin förälders hash.

I praktiken skriver du sällan ut en hel hash. De sju första tecknen räcker nästan alltid, och det
är därför `git log --oneline` visar just så många.

## Tre platser

En fil i ett Git-projekt kan befinna sig på tre ställen, och två kommandon flyttar den mellan dem.

En fil kan finnas på flera av platserna samtidigt, i olika versioner. Det är precis det `git status`
rapporterar när den säger *"Changes not staged for commit"*: filen på disken skiljer sig från den
som ligger i staging.

## Varför staging finns

Att `git add` behövs känns i början som ett onödigt extra steg.

Poängen är att du sällan gör en sak åt gången. Lisa fixar en bugg och råkar samtidigt rätta en
stavning i en annan fil. Utan staging måste båda in i samma commit.

Med staging lägger hon in bara buggfixen, committar den för sig, och tar stavfelet i en egen
commit. Resultatet är en historik där varje commit gör en begriplig sak — och det är skillnaden
mellan en historik man kan använda och en man skrollar förbi.

`git add -p` går ett steg längre och låter dig välja ändring för ändring inuti samma fil.

## `git add` vs `git commit`

Den vanligaste missuppfattningen om de två kommandona är att båda sparar. Bara det ena gör det.

**`git add`** flyttar filen till staging. Ingenting blir permanent, och kör du `git add` femton
gånger finns fortfarande ingen commit.

**`git commit`** tar det som ligger i staging och skriver en ögonblicksbild. Först nu finns något du
kan återvända till.

Följden märks när något går fel: har du bara kört `git add` och sedan skriver över filen är arbetet
borta. Staging är en förberedelse, inte en säkerhetskopia.

## Spårade vs ospårade filer

En fil som Git känner till kallas **spårad**. En fil som ligger i mappen men aldrig har lagts till
kallas **ospårad**.

Skillnaden avgör vad Git bryr sig om. Ospårade filer nämns i `git status` som en påminnelse, men
de kommer aldrig med i en commit förrän du lägger till dem.

Det är också den skillnaden som avgör vad `.gitignore` kan göra.

## `.gitignore`

`.gitignore` är en textfil som listar filer och mappar Git ska låta bli.

```txt
node_modules/
.env
*.log
```

Den används för sådant som antingen kan genereras om (`node_modules/`), är hemligt (`.env`) eller
är lokalt brus (`*.log`).

`.gitignore` påverkar bara **ospårade** filer. Har en fil redan committats en gång fortsätter Git
att spåra den, hur mycket den än står i `.gitignore`. Det är den vanligaste anledningen till att
raden "inte fungerar".

## De kommandon du faktiskt använder

Git har över hundra kommandon. I vardagen använder du ungefär sju.

```bash
git status               # var står mina filer?
git add prisberakning.js # lägg en fil i staging
git add -p               # välj ändring för ändring
git commit -m "Rätta momsberäkning för utlandet"
git log --oneline        # en rad per commit
git diff                 # arbetskatalog mot staging
git diff --staged        # staging mot senaste commit
```

<Callout type="sa-gor-du" title="Skriv commit-meddelanden någon kan använda">
Meddelandet är det enda som gör historiken sökbar. Skriv vad commiten **gör**, i imperativ, och
lägg *varför* i raderna under om det inte är uppenbart.

Bra: `Rätta momsberäkning för utländska kunder`
Sämre: `fix`, `wip`, `ändringar`, `funkar nu`

Testet: kommer någon som läser `git log` om ett halvår att förstå raden utan att öppna diffen?
</Callout>

## Fallgropen: historiken glömmer inte

<Callout type="fallgrop">
Lisa committar av misstag en `.env` med databaslösenordet. Hon upptäcker det, raderar filen,
committar igen — och tror att saken är löst.

Det är den inte. Den **första** ögonblicksbilden finns kvar, och lösenordet med den. Vem som helst
som klonar repot får hela historiken och kan läsa filen med ett kommando.

Två saker följer:

- Lägg in `.env` i `.gitignore` **innan** första commiten. Efteråt hjälper det inte, eftersom filen
  då redan är spårad.
- Har en hemlighet väl committats är den att betrakta som läckt. **Byt den.** Att städa historiken
  i efterhand är möjligt men jobbigt, och hjälper inte om någon redan klonat.
</Callout>

## Vad det här betyder i ditt arbete

Du kommer att köra `git status`, `git add`, `git commit` och `git log` varje dag, och resten av
Git kanske aldrig.

Ögonblicksbildsmodellen är ändå värd att förstå, för den förklarar det som annars känns
godtyckligt: varför en gren är gratis, varför `git diff` ibland visar tomt fast du ändrat något,
och varför en committad hemlighet inte går att radera bort.

Under huven ligger det mer — Git lagrar filinnehåll som **blobs** och kataloger som **trees**, och
en commit pekar på ett tree. De orden dyker upp i felmeddelanden, men du behöver dem inte för att
arbeta. De blir intressanta först den dag du felsöker ett trasigt repo.

## Vanliga nybörjarförväxlingar

Git är inte GitHub. Git skapar historiken lokalt; GitHub lagrar en kopia åt flera personer.

En commit sparar inte dina ändringar utan hela projektet. Diffen räknas ut vid behov.

`git add` sparar ingenting permanent. Den lägger filen i staging, och först `git commit` skriver
en ögonblicksbild.

`.gitignore` skyddar inte redan spårade filer, och den raderar inget som redan ligger i historiken.

Att radera en fil och committa tar inte bort filen ur historiken — bara ur den senaste
ögonblicksbilden.

## Prova själv

Gå till ett Git-projekt du redan har. Alla kommandon nedan bara läser.

```bash
git log --oneline | head -5
```

Du får fem rader, var och en med en kort hash och ett meddelande. Välj en hash och titta på vad
commiten faktiskt innehåller:

```bash
git cat-file -p a3f9c2e
```

Nu ser du commitens fyra delar i klartext: en rad `tree` (ögonblicksbilden), en rad `parent`
(föräldern), `author` och `committer` (metadata), och meddelandet sist.

Leta sedan upp den allra första commiten i repot:

```bash
git log --oneline | tail -1
git cat-file -p <hashen därifrån>
```

**Den saknar `parent`-raden.** Det är inte ett fel — det är kedjans början, den enda commit som
inte har någon före sig.

Två saker som kan förvirra: `git log` öppnas i en bläddrare som avslutas med `q`, och `tree`-raden
pekar på ett objekt, inte på en fil. Att följa `tree` vidare behöver du inte göra nu.

<Callout type="kom-ihag">
- En commit är en **ögonblicksbild av hela projektet** plus en pekare till föräldern — inte en
  lista med ändringar.
- Hashen räknas ut ur innehållet. Samma hash betyder garanterat samma kod.
- Tre platser: arbetskatalog → staging → repository. `git add` och `git commit` flyttar mellan dem.
- Staging finns för att du ska kunna committa **en sak i taget**, även när du gjort flera.
- `.gitignore` påverkar bara **ospårade** filer. En committad hemlighet är läckt — byt den.
</Callout>

## Snabb sammanfattning

- Git är ett versionshanteringssystem som körs lokalt och lagrar historiken i mappen `.git`.
- Git är inte GitHub. GitHub lagrar en kopia av ett Git-projekt åt flera personer.
- Ett repository är ett projekt Git håller reda på. `git init` skapar det.
- En commit är ett sparat läge — en ögonblicksbild av hela projektet, inte en lista med ändringar.
- En commit innehåller ögonblicksbilden, föräldern, metadata och en hash.
- Hashen räknas ut ur innehållet. Samma hash betyder garanterat samma kod.
- Tre platser: arbetskatalog → staging → repository. `git add` och `git commit` flyttar mellan dem.
- Staging finns för att du ska kunna committa en sak i taget, även när du gjort flera.
- Spårade filer följer Git; ospårade gör den inte. `.gitignore` påverkar bara ospårade.
- Historiken glömmer inte. En committad hemlighet är läckt och ska bytas.
