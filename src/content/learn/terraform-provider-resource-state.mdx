## Var vi är

Förra delen svarade på *varför*: infrastrukturen ska bo i textfiler som går att granska och köra om,
och Terraform gör det deklarativt. Slingan är skriv, `plan`, `apply`.

Den här delen öppnar filen och går igenom vad som faktiskt står i den — och den fil Terraform för
egna anteckningar i.

<Del titel="Språket" />

## Vad HCL är

**HCL**, HashiCorp Configuration Language, är språket Terraform-filer skrivs i.

Det är ett eget litet språk, men i praktiken består det av **block**: namngivna klamrar med
inställningar i. Kan du läsa ett block kan du läsa en hel Terraform-fil.

Filerna slutar på `.tf`. Terraform läser alla `.tf`-filer i mappen som en enda beskrivning, så hur
du delar upp dem är en fråga om läsbarhet, inte om funktion.

## Vad ett block är

Ett **block** har en typ, noll eller flera etiketter, och ett innehåll inom klamrar.

```hcl
resource "azurerm_resource_group" "rg" {
  name     = "rg-shop-prod"
  location = "swedencentral"
}
```

Här är `resource` blocktypen, `"azurerm_resource_group"` och `"rg"` är etiketterna, och raderna inom
klamrarna är argumenten.

Hur många etiketter ett block har bestäms av dess typ. `resource` tar två, `provider` tar en, och
`terraform` tar ingen.

## Filen, uppifrån och ner

Här är en komplett `main.tf` som skapar två saker i Azure åt Lisas e-handelssystem: en resursgrupp
och en app-plan att köra webben på.

```hcl
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

provider "azurerm" {
  features {}
}

resource "azurerm_resource_group" "rg" {
  name     = "rg-shop-prod"
  location = "swedencentral"
}

resource "azurerm_service_plan" "web" {
  name                = "asp-shop-prod"
  resource_group_name = azurerm_resource_group.rg.name
  location            = "swedencentral"
  os_type             = "Linux"
  sku_name            = "B1"
}
```

Tre sorters block, i den ordning de nästan alltid står. Vi tar dem ett i taget.

<Del titel="Blocken" />

## `terraform`-blocket

Det första blocket handlar inte om molnet alls — det handlar om Terraform självt.

Här står vilka **providers** projektet är beroende av och vilka versioner som duger.
`source = "hashicorp/azurerm"` pekar ut paketet i Terraform Registry.

Blocket är också där en delad lagringsplats för state konfigureras, vilket vi kommer till längre ner.

## Varför versionen ska stå där

`version = "~> 4.0"` betyder "4.x, men inte 5.0". Nya rättningar hämtas automatiskt, men inte en ny
huvudversion som kan innehålla brytande ändringar.

<Callout type="varfor" title="Vad som händer utan versionsgräns">
Utan gräns hämtar varje utvecklare — och pipelinen — den senaste providern som råkar finnas den
dagen. Samma fil kan då ge olika resultat hos olika personer.

Det är exakt samma problem som `FROM node:latest` i en Dockerfile: bygget slutar vara reproducerbart.
</Callout>

## Vad en provider är

En **provider** är ett insticksprogram som översätter dina block till anrop mot en leverantörs API.

Terraform kan i sig ingenting om Azure. Den vet inte vad en resursgrupp är, vilket API som ska
anropas eller hur inloggningen går till. Allt det ligger i providern.

Prefixet på en resurstyp avslöjar vilken provider som äger den. Allt som börjar med `azurerm_` kommer
från Azure-providern.

## `provider`-blocket

Medan `terraform`-blocket säger *vilken* provider som behövs, är `provider`-blocket där providerns
egna inställningar hamnar: prenumeration, region, autentisering.

```hcl
provider "azurerm" {
  features {}
}
```

`features {}` ser tomt ut men är obligatoriskt för Azure-providern. Utan blocket vägrar `terraform
plan` köra — och det är ett fel `terraform validate` inte upptäcker, vilket vi provar i slutet.

## Vad en resource är

Ett **resource**-block beskriver **en sak som ska existera**.

Det är arbetshästen i varje Terraform-fil. En resursgrupp, en databas, en DNS-post, en
lagringsbehållare — allt beskrivs som en resource.

Innehållet i blocket är inställningarna för just den resurstypen, och vilka som finns bestäms av
providern.

## Resurstyp vs resursnamn vs `name`

Tre namn i samma block, och att blanda ihop dem är det vanligaste nybörjarfelet i HCL.

```text
resource                  nyckelordet
"azurerm_resource_group"  typen — providern bestämmer
"rg"                      namnet — du bestämmer
```

**Typen** säger *vad* det är. Den kommer från providern och går inte att hitta på.

**Resursnamnet** är ditt eget handtag. Det används bara inne i din egen kod, för att kunna peka på
resursen från andra block. Det syns aldrig i Azure.

**Argumentet `name`** är vad resursen faktiskt heter hos leverantören.

Att skilja på de två sista är värt en extra sekund: `name = "rg-shop-prod"` är vad resursen heter
**i Azure**. `"rg"` är adressen Terraform använder **i din fil och i state**. När du byter den ska
du tala om flytten med ett `moved`-block eller `terraform state mv`, så att Terraform behåller
kopplingen till samma resurs.

<Doodle name="tre-namn-i-blocket" caption="Tre understrukna delar, tre pilar, tre olika ägare." />

## Vad en referens är

En **referens** pekar på en annan resurs, i formen `typ.namn.attribut`.

```hcl
resource_group_name = azurerm_resource_group.rg.name
```

Här hämtar app-planen resursgruppens namn i stället för att upprepa strängen. Det är inte bara ett
sätt att slippa skriva samma sak två gånger — det är så Terraform får reda på **ordningen**.

## Beroendegrafen

Terraform läser alla referenser i filen och bygger en **beroendegraf**.

Eftersom app-planen refererar till resursgruppen måste resursgruppen skapas först. Du kan flytta om
blocken i filen hur du vill — resultatet blir detsamma, för ordningen kommer från referenserna och
inte från raderna.

<Callout type="fallgrop">
Skriver du i stället `resource_group_name = "rg-shop-prod"` som en hårdkodad sträng ser Terraform
ingen koppling alls.

Resultatet fungerar oftast — tills det inte gör det. Terraform kan då råka försöka skapa app-planen
först, och du får ett fel som ser slumpmässigt ut eftersom det beror på i vilken ordning saker råkade
köras.

Referera alltid i stället för att upprepa. Beroendet blir en bieffekt du får gratis.
</Callout>

`init` är alltså inte valfritt. Det installerar de providers och moduler konfigurationen behöver och
initierar den valda backenden. Utan providern vet Terraform ingenting om
`azurerm_resource_group`.

Det finns ett fjärde: `terraform destroy` river allt som beskrivningen äger. Det låter dramatiskt men
är precis det man vill ha i en testmiljö som bara ska leva över en demonstration.

## Vad state är

**State** är Terraforms anteckning om de resurser den hanterar.

När `apply` skapat resursgruppen skriver Terraform ner vad den gjorde i en fil som heter
`terraform.tfstate`: vilka resurser som finns, vilka id:n de har hos leverantören och de värden
Terraform behöver för att jämföra dem med konfigurationen.

En befintlig resurs kan också tas in i state med import. Filen skapas och läses av Terraform, och du
ska normalt aldrig redigera den för hand.

<Doodle name="state-triangeln" caption="Två heldragna pilar ut från filen, en streckad mellan de två nedre." />

## State vs konfigurationsfilen

De två filerna ser besläktade ut och gör motsatta saker.

**`main.tf`** är önskemålet. Den skriver du, den ligger i Git, och den beskriver hur det *ska* se ut.

**`terraform.tfstate`** är anteckningen. Terraform skriver den, den ligger inte i Git, och den
beskriver vad som *redan finns*.

Utan state kan Terraform inte skilja *ändra* från *skapa*:

## Lokal state vs remote backend

Var filen ligger avgör om fler än en person kan arbeta i projektet.

**Lokal state** ligger som `terraform.tfstate` i din projektmapp. Det fungerar så länge du övar
ensam.

**En remote backend** lägger state på en delad lagringsplats som alla kör mot. Många backender kan
också låsa state så att samtidiga ändringar inte krockar; kontrollera hur den valda backenden
konfigurerar låsning.

<Callout type="fallgrop">
Ligger state lokalt hos dig har **Maria en egen kopia** — eller ingen alls. Hennes Terraform tror att
inget finns och försöker skapa allt en gång till. Kör ni dessutom samtidigt kan ni skriva över
varandras ändringar mitt i.

Lösningen konfigureras i `terraform`-blocket:

```hcl
terraform {
  backend "s3" {
    bucket       = "shop-tfstate"
    key          = "prod/terraform.tfstate"
    region       = "eu-north-1"
    use_lockfile = true
  }
}
```
</Callout>

State ska heller aldrig in i Git. Den innehåller ofta genererade lösenord och nycklar i klartext.
Lägg `terraform.tfstate*` och `.terraform/` i `.gitignore`.

## State vs låsfilen

Två filer som båda skapas av Terraform och behandlas tvärtom.

**`terraform.tfstate`** beskriver en specifik miljös verkliga innehåll, rymmer ofta hemligheter och
hör hemma i en delad backend. **Aldrig i Git.**

**`.terraform.lock.hcl`** spikar exakt vilka provider-versioner projektet använder, så att alla —
inklusive pipelinen — får samma. **Alltid i Git.**

Namnen liknar varandra och innehållet är helt olika. Låsfilen har heller ingenting med låset i en
remote backend att göra; den låser versioner, inte samtidiga körningar.

<Del titel="Öva och förstå" />

## Vad det här betyder i ditt arbete

Du kommer att läsa `.tf`-filer oftare än du skriver dem, och när du skriver är det oftast tio rader
kopierade från ett block som redan finns.

Det du behöver kunna på riktigt är att läsa ett `plan`-utfall och veta vilket block varje rad hör
till — och att aldrig hårdkoda något du kan referera.

När fler än en person eller pipeline arbetar mot samma miljö behöver teamet en delad state-lösning
med lämplig åtkomst och, när backenden stöder det, låsning.

Moduler, variabler, `for_each` och workspaces kan vänta. De är sätt att slippa upprepa block, och de
bygger alla på de tre blocktyperna i den här delen.

## Vanliga nybörjarförväxlingar

Resurstypen är inte resursnamnet. Typen kommer från providern, namnet väljer du.

Resursnamnet är inte `name`. Det ena syns bara i din fil, det andra hos leverantören.

Terraform hämtar inte providern automatiskt. `init` förbereder providers, moduler och backend.

Blockens ordning i filen styr ingenting. Referenserna gör det.

`terraform.tfstate` och `.terraform.lock.hcl` är inte samma sorts fil. Den ena ska aldrig in i Git,
den andra alltid.

`terraform validate` kontrollerar inte att providern är konfigurerad. Den kan säga *Success* om en
fil som `plan` vägrar köra.

## Prova själv

Du behöver Terraform installerat, men **inget molnkonto** — övningen stannar innan något skapas.

Skapa en mapp, lägg `main.tf` från avsnittet "Filen, uppifrån och ner" i den, och kör:

```bash
terraform init
```

Titta på vad som dök upp i mappen:

```bash
ls -a
```

Där ligger nu `.terraform/` med providern och `.terraform.lock.hcl` med versionerna. **Någon
`terraform.tfstate` finns inte** — den skapas först av `apply`, och du har inte kört något än.

Öppna låsfilen:

```bash
head -8 .terraform.lock.hcl
```

Du ser vilken exakt providerversion som valdes, och villkoret `~> 4.0` den valdes inom.

Ta nu bort hela `provider "azurerm"`-blocket ur filen och kör:

```bash
terraform validate
```

Den svarar `Success! The configuration is valid.` Kör sedan:

```bash
terraform plan
```

Nu får du `Error: Invalid provider configuration`. **Samma fil, två olika besked** — och det är
poängen: `validate` kontrollerar syntax och att argumenten finns, inte att providern är konfigurerad.

Sätt tillbaka blocket när du är klar. Kommer du längre än så beror på om du har inloggning mot Azure,
vilket ligger utanför den här övningen.

Två saker som kan förvirra: `init` hämtar providers och moduler över nätet och tar därför längre tid
första gången. Och `.terraform/` kan bli stor beroende på providers och moduler — den hör därför
hemma i `.gitignore`, inte i repot.

## Snabb sammanfattning

- HCL består av block: en blocktyp, noll eller flera etiketter, och argument inom klamrar.
- Terraform läser alla `.tf`-filer i mappen som en enda beskrivning.
- `terraform`-blocket säger vad projektet behöver och vilka versioner som duger.
- Versionsgräns är inte pedanteri. Utan den slutar bygget vara reproducerbart.
- Providern översätter dina block till API-anrop. Prefixet på resurstypen visar vilken.
- `provider`-blocket bär providerns egna inställningar. För Azure är `features {}` obligatoriskt.
- Ett `resource`-block beskriver en sak som ska existera.
- Typen kommer från providern, resursnamnet är ditt handtag, `name` är namnet hos leverantören.
- Referenser i formen `typ.namn.attribut` bygger beroendegrafen. Hårdkodade strängar gör det inte.
- `init` förbereder backend, moduler och providers. `plan` visar, `apply` genomför. `destroy` river.
- State är Terraforms anteckning om resurser den hanterar. Import kopplar en befintlig resurs till
  state.
- State i delad backend, aldrig i Git. Använd låsning när backenden stöder det. Låsfilen alltid i Git.
- `validate` kontrollerar inte provider-konfiguration. Det gör `plan`.

## Nästa del

Härifrån är nästa steg att sluta hårdkoda värden och börja återanvända: variabler, outputs och
moduler, så att samma beskrivning kan sätta upp både test och produktion.
